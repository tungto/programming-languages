Part I

How to think about any construct

One habit that covers the whole course: ask three questions of each new thing.

1Syntax, type-check, evaluate

Every new language construct is learned by answering three questions: what is the syntax, how does it type-check, how does it evaluate. [summary p.2]

Type-checking uses the static environment (names → types) before the program runs. Evaluation uses the dynamic environment (names → values) while it runs.

val x = 34;        (* static env: x : int      dynamic env: x --> 34 *)
val y = x + 1;     (* static env: y : int      dynamic env: y --> 35 *)
val z = if y > 0 then 0 else x + 1;
QuestionAsked whenUses

Try first: Give the three rules for if e1 then e2 else e3.

Hint: there are two type rules

Syntax: keywords if/then/else with three subexpressions. Type-check: e1 must be bool; e2 and e3 must have the same type t, which is the type of the whole. Evaluate: evaluate e1; if true, result is e2's value, else e3's value - only one branch runs.

Lecture code: 3_our_first_program.sml

2Bindings are immutable; shadowing is not mutation

A val binding can never be changed; a later binding with the same name only shadows it in a new environment. [summary p.4]

val a = 10
val f = fn () => a     (* f will use the a that exists HERE *)
val a = 5              (* new binding, shadows the old a *)
val r = f ()           (* r = 10, not 5 *)
Easy to get wrong: "val a = 5 changes a"

Wrong: a now equals 5 everywhere. Right: code written before still sees the old binding; only later code sees the new one.

Try first: After val a = 1; val b = a * 2; val a = 3; what is b?

2. b was computed from the a in its environment at that time; the later a does not reach back.

Lecture code: 6_shadowing.sml

3Using use and the REPL

use "file.sml"; evaluates every binding in the file and adds them to the REPL's environment, as if typed one by one. [summary p.3]

Easy to get wrong: re-running use in the same REPL

Calling use twice shadows old bindings but keeps stale ones around. Restart the REPL before re-loading a file.

Lecture code: 10_repl.txt, 5_some_errors.sml, 5_errors_fixed.sml

Part II

Building values

Functions, tuples and lists: the three ways to compute with and combine data in Section 1.

4Function bindings

fun f (x1 : t1, ..., xn : tn) = e has type t1 * ... * tn -> t; a call evaluates the arguments, then evaluates the body in the environment where the function was defined, extended with the arguments. [summary p.4]

Recursion works because f is in the environment of its own body. Functions are values: binding them adds f to the environment, nothing runs yet.

fun pow (x : int, y : int) =     (* y >= 0 *)
    if y = 0 then 1 else x * pow (x, y - 1)

fun cube (x : int) = pow (x, 3)
val ans = cube 4                  (* 64 *)
Try first: What is the type of pow? Why does the argument list look like a tuple type?

int * int -> int. In ML every function takes exactly one argument; "multiple arguments" are really one tuple (shown fully in Section 2).

Lecture code: 7_functions.sml

5Pairs and other tuples

A tuple (e1, e2) has type t1 * t2; read parts with #1 e, #2 e. Tuples can nest and hold any types. [summary p.5]

fun swap (pr : int * bool) = (#2 pr, #1 pr)    (* bool * int *)
fun div_mod (x : int, y : int) = (x div y, x mod y)
val nested = (1, (true, 3.0))                    (* int * (bool * real) *)
Try first: What is the type of #1 (#2 nested)?

bool.

Lecture code: 9_tuples.sml

6Lists

A list holds any number of elements of one type; build with [] and :: (cons), read with null, hd, tl. [summary p.6]

Functions over lists are almost always recursive: one case for the empty list, one for hd combined with a recursive call on tl.

fun sum_list (xs : int list) =
    if null xs then 0 else hd xs + sum_list (tl xs)

fun countdown (x : int) =                 (* countdown 3 = [3,2,1] *)
    if x = 0 then [] else x :: countdown (x - 1)

fun append (xs : int list, ys : int list) =
    if null xs then ys else hd xs :: append (tl xs, ys)

Easy to get wrong: hd [] and :: on the wrong side

hd and tl raise an exception on []. The left of :: is one element, the right is a list: 1 :: [2] works, [1] :: 2 does not.

Try first: Write firsts : (int*int) list -> int list from blank.

Hint: base case first, then cons onto the recursive call

fun firsts (xs : (int*int) list) = if null xs then [] else (#1 (hd xs)) :: firsts (tl xs)

Part III

Structure and safety

Local bindings, efficiency, options, and why no mutation helps.

7Let expressions

let b1 ... bn in e end makes local bindings visible only in later bindings and in e; the whole is an expression with e's value. [summary p.8]

Local helper functions can use the outer function's arguments directly, so they need fewer parameters.

fun count_from1 (x : int) =
    let fun count (from : int) =
            if from = x then x :: [] else from :: count (from + 1)
    in count 1 end

Lecture code: 12_let_expressions.sml, 13_nested_functions.sml

8Let for efficiency: don't recompute

Calling the same recursive function twice on the same input in one branch makes the run time exponential; bind the result once with let. [summary p.9]

(* bad: two recursive calls -> 2^n work *)
fun bad_max (xs : int list) =
    if null (tl xs) then hd xs
    else if hd xs > bad_max (tl xs) then hd xs else bad_max (tl xs)

(* good: one recursive call, bound once *)
fun good_max (xs : int list) =
    if null (tl xs) then hd xs
    else let val tl_ans = good_max (tl xs)
         in if hd xs > tl_ans then hd xs else tl_ans end
Try first: For a 30-element list sorted ascending, roughly how many calls does bad_max make?

About 2^30 (a billion): every level calls itself twice. good_max makes 30.

Lecture code: 14_let_efficiency.sml

9Options

t option holds either NONE or SOME e: use it instead of a fake answer when a result may not exist. Read with isSome and valOf. [summary p.10]

fun max1 (xs : int list) =
    if null xs then NONE
    else let val tl_ans = max1 (tl xs)
         in if isSome tl_ans andalso valOf tl_ans > hd xs
            then tl_ans else SOME (hd xs) end
Easy to get wrong: valOf NONE

valOf raises an exception on NONE. Check isSome first (or, from Section 2, use a case expression).

Lecture code: 15_options.sml

11No mutation, and why it helps

Because nothing can be mutated, sharing and copying are indistinguishable: callers never worry about aliasing. [summary p.11]

In Java, returning an internal array lets a caller change your object's state - a real security bug pattern. In ML, returning tl xs shares memory safely, since no one can change it.

fun sort_pair (pr : int * int) =
    if #1 pr < #2 pr then pr else (#2 pr, #1 pr)   (* returning pr itself is safe *)
Try first: In JavaScript, why is return this.items risky but in ML the same idea is not?

JS arrays are mutable: the caller can push into your internal state. ML lists are immutable, so returning the alias equals returning a copy.

13In short

  • Learn each construct by its syntax, type-check rule and evaluation rule.
  • Bindings never change; shadowing adds a new binding and old code keeps seeing the old one.
  • Lists are recursive: one case for [], one for hd + recursive call on tl.
  • Never make the same recursive call twice - bind it once with let.
  • Use options instead of fake values; no mutation makes aliasing safe.
