Key words for inference and modules

The words Section 4 uses for type inference, modules and equivalence, in plain English. Read before the study guide. It is a word list, not the algorithm.

Source · section4sum.pdfTime · 25-35 minRecommended · the section summary, after this page

1How to use this page

Cover the meaning and say each word in your own words first. Then open the card. Each card has: a plain meaning, the smallest example, what it is not, and a picture to remember it.

Words in bold inside a meaning are the part to remember. Page links go to the exact page in the section summary.

Why words come first

The summary explains each idea using other key words. If one word is fuzzy, the whole sentence is fuzzy. Fixing the words fixes most of the confusion.

2Typing words

Section 4 opens by separating three ideas people mix up.

Try first: say one sentence for each word before reading the cards

Statically typed, Implicitly typed, Infer, Constraint, Unconstrained, Contradiction, Sound / unsound, Mutual recursion (and), Finite state machine

Statically typed

Types are checked before running. ML, Java, C.

Not the same asDynamically typed: types checked while running (Racket, Python, JS).

summary p.1

Implicitly typed

You rarely write types; the compiler finds them. ML is implicit and static.

Not the same asExplicit: you write them (Java).

summary p.1

Infer

Work out from clues. Type inference = working out the types you did not write.

Picture itA detective using clues.

summary p.1

Constraint

A fact the checker learns from code, like "T3 = int" because of abs y.

fun f x = let val (y, z) = x in abs y + z end
(* x is a pair; y : int; z : int *)

summary p.3

Unconstrained

A type no code limits. It becomes 'a.

fun f (y, z, w) = if y then z + 1 else 0   (* w : 'a *)

summary p.4

Contradiction

Two constraints that cannot both be true, like T = T list. The type error.

summary p.4

Sound / unsound

Sound type system: an accepted program never uses a value at the wrong type. The value restriction keeps ML sound.

summary p.6

Mutual recursion (and)

Two functions that call each other. Joined with and.

fun even n = ... odd (n - 1)
and odd n = ... even (n - 1)

summary p.7

Finite state machine

A set of states and rules for moving between them. One function per state is a neat way to code it.

summary p.7

3Module words

Words for grouping code and hiding details.

Try first: say one sentence for each word before reading the cards

Module / structure, Namespace, open, Signature, Interface vs implementation, Abstract type, Invariant, Property / specification, Signature matching

Module / structure

A named group of bindings. In ML a module is written as a structure.

structure M = struct val x = 1 end   (* use M.x *)

Picture itA folder.

summary p.9

Namespace

A space where names live, so List.map and Tree.map do not clash.

summary p.9

open

Lets you write x instead of M.x. Fine for tests; risky elsewhere (shadowing).

open M

summary p.9

Signature

A type for a module: what it must provide and what outsiders may see.

signature S = sig val fact : int -> int end

Picture itA TypeScript interface for a whole file.

summary p.9

Interface vs implementation

Interface = what clients may use. Implementation = how it is done inside.

Picture itA restaurant menu vs the kitchen.

summary p.10

Abstract type

type t in a signature with no definition: clients know it exists, not what it is.

type rational   (* clients cannot see Frac/Whole *)

summary p.13

Invariant

A fact about the data the module always keeps true inside, e.g. "denominator > 0".

Not the same asProperty: the promise to clients, outside.

summary p.11

Property / specification

What the module promises clients, e.g. "toString is always reduced".

summary p.12

Signature matching

Whether a structure has everything its signature asks for, at the same or a more general type.

Not the same asNot pattern matching.

summary p.14

4Equivalence words

Words for "is this change safe?".

Try first: say one sentence for each word before reading the cards

Equivalent, Observable, Pure functional, Asymptotic complexity

Equivalent

Two pieces of code that no client can tell apart: same result, termination, mutation, I/O, exceptions.

fun f x = x + x     fun f x = 2 * x

summary p.18

Observable

Something a client can see. Speed and helper functions are unobservable for this definition.

summary p.18

Pure functional

A language where functions cannot have side effects.

summary p.19

Asymptotic complexity

How running time grows with input size (big-O). A stricter view of equivalence.

summary p.21

Try first: In fun g (a, b) = a, why is b's type 'b?

Nothing in the body constrains b, so it stays unconstrained.

Try first: Invariant or property: "no denominator is ever 0" written in a comment inside the structure?

Invariant: an internal fact. The property is what clients are promised.
